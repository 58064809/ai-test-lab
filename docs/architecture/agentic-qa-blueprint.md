# Agentic QA 建设蓝图

---

## 1. 文档定位

本文用于定义本仓库 Agentic QA 主线的建设思路，回答以下问题：

- Agentic QA 要解决什么质量问题
- Agent 应该具备哪些测试能力
- 人、Agent、工具链之间如何协作
- 哪些任务可以自动化，哪些任务必须人工审核
- 当前仓库后续可以如何演进

本文是 Agentic QA 主线的建设蓝图。它不替代 `AGENTS.md`、`standards/`、`skills/` 或 `templates/`，而是用于指导后续如何把 Agentic QA 能力拆分并沉淀到这些层次中。

---

## 2. 使用前置要求

在基于本文进行 Agentic QA 方案设计、Agent 定义、Skill 编写、Template 设计或工程实现前，必须先参考：

- `references/research/agentic-qa-research-guide.md`

该调研指南用于提供外部产品、Agent 框架、MCP、浏览器 Agent 和测试报告平台的资料入口。本文负责沉淀“本仓库怎么做”，调研指南负责说明“外部资料怎么看、哪些能力值得借鉴”。

两份文档不建议合并：

- 本文是建设蓝图，强调目标、能力边界、工作流和落地路线
- 调研指南是资料索引，强调阅读顺序、资料来源、调研产出和外部能力参考

如果合并，会让蓝图文档被链接和调研笔记稀释，降低后续维护性。

## 4. 核心结论

Agentic QA 的价值不在于让 AI 生成一段测试文本，而在于把需求、代码变更、接口文档、UI 页面、日志、测试报告等输入接入测试工作流，让 Agent 能够辅助完成风险分析、测试设计、测试执行、失败归因、缺陷整理和质量结论输出。

但 Agentic QA 不能一开始就追求完全无人化。更合理的落地方式是：

- 低风险任务：允许 Agent 自动完成
- 中风险任务：Agent 生成结果，人审核后执行
- 高风险任务：Agent 只给建议，人必须确认

核心目标是形成“Agent 辅助判断 + 工具链执行 + 人工质量把关 + 结果可追踪”的闭环。

结合 `references/research/agentic-qa-research-guide.md` 中的外部资料，当前方案吸收以下判断：

- 商业平台更强调测试生命周期闭环，而不是单点文本生成
- Agent 框架的关键价值在于工作流编排、工具调用、人工审核、Guardrails 和 Tracing
- 浏览器 Agent 适合辅助 UI 探索、用例生成和自愈建议，但稳定回归仍应沉淀为可维护自动化脚本
- 报告和质量分析平台的价值在于失败归因、趋势分析和发布决策支持

## 5. 建设目标

Agentic QA 体系应服务于以下目标：

1. 提升测试分析效率  
   让 Agent 快速读取需求、变更、接口、日志和报告，辅助识别风险和测试范围。

2. 提升测试设计完整性  
   让 Agent 按统一标准生成测试点、测试用例、边界场景、异常场景和回归建议。

3. 提升自动化资产维护效率  
   让 Agent 辅助生成、更新和修复 API/UI 自动化测试脚本。

4. 提升失败分析效率  
   让 Agent 基于日志、堆栈、截图、请求响应和报告进行失败归因，并输出证据链。

5. 提升质量决策可解释性  
   让测试结论、发布建议、风险判断具备明确依据，而不是只给模糊结论。

6. 沉淀可复用测试资产  
   将 Prompt、测试知识库、用例、脚本、质量门禁、评估标准和报告模板沉淀为团队资产。

当前阶段不追求一次性建设完整平台。优先验证 1 到 2 个高价值闭环，再逐步拆分 Agent、Skill、Template 和工程支撑。

## 6. 核心能力范围

| 能力模块 | 主要输入 | 主要输出 | 关键边界 |
| --- | --- | --- | --- |
| 需求与风险分析 | PRD、用户故事、验收标准、历史缺陷 | 风险点、疑问清单、测试范围建议 | 不能替代产品确认业务规则 |
| 测试设计 | 需求、接口文档、业务规则、历史用例 | 测试点、测试用例、边界场景、异常场景 | 需要人工审核核心业务覆盖 |
| 精准回归 | Git diff、PR 信息、影响文件、历史失败记录 | 回归清单、风险级别、执行建议 | 不能只依赖代码路径判断影响范围 |
| API 测试生成 | OpenAPI、接口文档、请求示例、数据库规则 | 接口用例、断言、契约测试、数据校验 | 不得编造接口字段或业务规则 |
| UI 自动化辅助 | 页面结构、流程说明、已有脚本、失败截图 | UI 用例、locator 建议、自愈建议 | 自愈结果必须校验业务语义 |
| 测试数据治理 | 数据模型、业务状态、环境约束、造数规则 | 测试数据方案、清理策略、隔离策略 | 写数据操作必须受权限控制 |
| 自动化执行 | Pytest、Playwright、Postman、JMeter、CI | 执行结果、失败用例、报告链接 | 高风险环境禁止无审批执行 |
| 失败智能分析 | 日志、堆栈、截图、Allure、Jenkins、请求响应 | 失败摘要、根因判断、证据链、重跑建议 | 不得把推测原因写成确认结论 |
| 缺陷归类 | 失败分析、历史缺陷、影响范围 | Bug 草稿、优先级建议、影响范围 | 缺陷提交建议由人最终确认 |
| 质量报告 | 测试计划、执行结果、缺陷列表、历史趋势 | 测试结论、阻塞风险、发布建议 | 发布结论必须绑定门禁规则 |
| AI 输出评估 | Agent 输出、人工审核结果、执行反馈 | 正确性、完整性、可执行性评估 | 评估标准要长期沉淀和复用 |
| 权限与审计 | Agent 操作记录、工具调用、审批记录 | 审计日志、权限边界、异常追踪 | 生产操作默认禁止或强审批 |

## 7. 推荐工作流

推荐的端到端工作流如下：

```text
需求 / 用户故事 / PR / 缺陷 / 测试报告
        ↓
Agent 读取上下文并识别任务类型
        ↓
Agent 分析风险、范围和缺口
        ↓
Agent 生成测试计划、测试点或执行建议
        ↓
Agent 调用工具生成或执行测试
        ↓
CI / 自动化框架 / 测试平台返回结果
        ↓
Agent 分析失败、整理证据链和缺陷草稿
        ↓
人审核关键判断、确认风险和发布建议
        ↓
沉淀用例、规则、知识库、评估结果和审计记录
```

关键原则：

- Agent 负责辅助分析、生成、执行和归因
- 工具链负责真实读取、执行、查询和报告
- 人负责高风险判断、业务语义确认和最终质量决策
- 所有重要结论都应保留证据链

## 8. Agent 分工建议

| Agent | 负责内容 |
| --- | --- |
| Requirement Analysis Agent | 分析需求、识别风险、提出疑问、判断可测试性 |
| Test Design Agent | 生成测试点、测试用例、边界场景、异常场景 |
| API Test Agent | 根据接口文档生成 API 测试、契约测试和接口断言 |
| UI Test Agent | 根据页面或流程生成 UI 测试建议和自动化脚本草稿 |
| Test Data Agent | 准备、清理、隔离和治理测试数据 |
| Execution Agent | 调用 Pytest、Playwright、Postman、JMeter、CI 等执行测试 |
| Failure Analysis Agent | 分析日志、截图、报告、堆栈和请求响应 |
| Defect Triage Agent | 归类缺陷、判断优先级、生成 Bug 草稿 |
| Regression Selection Agent | 根据代码变更、历史缺陷和风险选择回归范围 |
| Report Agent | 输出测试报告、风险结论和发布建议 |
| Orchestrator | 负责任务路由、上下文编排、工具调用和结果汇总 |

注意：默认不应为了“看起来完整”而同时启用全部 Agent。一个任务应优先选择一个主 Agent，只有当风险跨多个测试场景时才引入协同。

## 9. 工具链接入范围

Agentic QA 不能只停留在聊天页面，应逐步接入真实研发与测试工具链。

| 类型 | 工具示例 | 接入目的 |
| --- | --- | --- |
| 需求/文档 | Jira、Confluence、飞书文档、Notion、Markdown | 读取需求、验收标准和评审记录 |
| 代码仓库 | GitHub、GitLab、Gitee | 分析 diff、PR、影响文件和变更历史 |
| 自动化框架 | Pytest、Playwright、JUnit、TestNG、Cypress | 生成、执行和维护自动化测试 |
| API 工具 | Postman、Apifox、OpenAPI/Swagger | 生成接口用例、断言和契约测试 |
| CI/CD | Jenkins、GitHub Actions、GitLab CI | 触发执行、读取构建结果和失败记录 |
| 报告系统 | Allure、ReportPortal、JUnit XML | 汇总测试结果和失败证据 |
| 日志系统 | ELK、Loki、CloudWatch、应用日志 | 辅助失败归因和问题定位 |
| 监控系统 | Prometheus、Grafana、Datadog | 分析稳定性、性能和环境问题 |
| 缺陷系统 | Jira、禅道、TAPD、飞书项目 | 生成缺陷草稿、关联缺陷状态 |
| AI/Agent 框架 | LangGraph、CrewAI、AutoGen、Responses API、MCP | 实现编排、工具调用、上下文管理和审计 |

核心不是接入工具数量，而是让 Agent 真正能读、能跑、能查、能判断，并能留下可追踪依据。

## 10. 典型场景设计

### 10.1 需求到测试用例自动生成

输入：

- 用户故事
- PRD
- 验收标准
- 接口文档
- 历史缺陷

Agent 输出：

- 测试范围
- 测试点
- 正向用例
- 异常用例
- 边界用例
- 兼容性用例
- 接口用例
- 回归建议
- 风险问题清单

人工审核重点：

- 核心业务链路是否覆盖
- 验收标准是否被正确理解
- 是否遗漏权限、状态、数据一致性和异常路径
- 是否存在 Agent 编造规则或字段

### 10.2 代码变更驱动精准回归

输入：

- Git diff
- PR 信息
- 影响文件
- 接口变更
- 数据库变更
- 历史缺陷
- 历史失败记录

Agent 判断：

- 改动影响哪些模块
- 哪些接口需要测试
- 哪些 UI 流程需要回归
- 哪些历史 Bug 可能复发
- 哪些自动化用例需要执行
- 是否需要人工探索测试

输出：

- 精准回归测试清单
- P0/P1/P2 风险级别
- 自动化执行计划
- 人工补充测试建议

核心价值：

企业真实痛点通常不是“没有回归测试”，而是每次发版不知道应该回归多少。精准回归应优先服务于高风险变更和核心链路，而不是追求表面覆盖率。

### 10.3 自动化失败智能分析

输入：

- 报错堆栈
- 请求响应
- 数据库数据
- 截图
- Allure 报告
- Jenkins 日志
- 应用日志

失败归因维度：

| 失败类型 | 可能原因 |
| --- | --- |
| 脚本问题 | 选择器失效、断言错误、等待不足 |
| 数据问题 | 前置数据不存在、状态不符合、脏数据 |
| 环境问题 | 服务不可用、网络超时、依赖异常 |
| 业务 Bug | 返回值错误、状态流转错误、金额计算错误 |
| 第三方问题 | 支付、短信、OCR、风控服务异常 |
| 非稳定失败 | flaky、偶发超时、并发冲突 |

输出：

- 失败摘要
- 根因判断
- 证据链
- 影响范围
- 是否建议提 Bug
- 建议修复方向
- 是否建议重跑

约束：

根因判断必须区分“已确认事实”“合理推断”和“待确认项”，不能把推测原因写成确定结论。

### 10.4 UI 自动化自愈维护

传统 UI 自动化的主要痛点是前端页面变更后 locator 失效。

Agent 可辅助完成：

- 识别元素变化
- 尝试替代定位方式
- 分析页面结构
- 更新 locator 建议
- 判断是否为真实 Bug
- 标记高风险变更

风险提醒：

自愈不等于永远正确。比如按钮文案从“提交订单”变成“确认支付”，即使 locator 可以自动修复，业务含义也可能已经变化。这类场景必须人工审核。

### 10.5 Agentic API Testing

输入：

- OpenAPI/Swagger
- 接口文档
- 请求示例
- 数据库表结构
- 历史接口用例

Agent 生成：

- 正常参数用例
- 必填缺失用例
- 边界值用例
- 枚举值用例
- 权限用例
- 幂等性用例
- 并发用例
- 契约测试
- 接口断言
- 数据库断言

进一步能力：

- 自动识别接口字段变化
- 判断是否破坏兼容性
- 生成差异测试
- 更新测试数据建议

### 10.6 质量报告自动总结

输入：

- 测试计划
- 用例执行结果
- Allure 报告
- Jenkins 构建结果
- 缺陷列表
- 失败日志
- 历史趋势

输出：

- 本次测试结论
- 阻塞问题
- 高风险模块
- 失败用例归因
- 是否建议发布
- 需要产品/开发确认的问题
- 下一轮回归建议

适用对象：

- QA Lead
- 测试经理
- 发布负责人
- 项目质量负责人

## 11. AI 输出可信度评估

Agent 输出必须被评估，而不是默认可信。

| 评估维度 | 说明 |
| --- | --- |
| 完整性 | 是否覆盖核心业务路径、异常路径、边界条件 |
| 正确性 | 用例、断言、数据是否符合真实业务规则 |
| 可执行性 | 脚本是否能运行，依赖是否清楚 |
| 可维护性 | 是否有清晰分层、复用和命名规范 |
| 可追溯性 | 用例能否追溯到需求、代码变更和缺陷 |
| 稳定性 | 是否容易 flaky，是否受环境影响 |
| 安全性 | 是否泄露敏感数据，是否错误操作生产环境 |
| 可解释性 | Agent 为什么这样判断，依据是什么 |

常见风险：

- 漏掉关键测试场景
- 生成错误断言
- 编造接口字段
- 误判失败原因
- 忽略业务前置条件
- 生成不可执行脚本
- 把环境问题判断成代码问题

## 12. Human-in-the-loop 与权限边界

| 场景 | 自动化程度 | 审核要求 |
| --- | --- | --- |
| 生成测试点 | 可自动生成 | 人审核核心链路和风险点 |
| 生成用例草稿 | 可自动生成 | 人抽检或按风险审核 |
| 执行只读测试 | 可自动执行 | 需要限制环境和账号权限 |
| 查询测试数据库 | 可自动执行 | 只读账号，记录查询日志 |
| 修改测试数据 | 受控执行 | 需要审批或沙箱环境 |
| 线上环境操作 | 默认禁止 | 特殊情况强审批 |
| 自动提 Bug | 生成草稿 | 人确认后提交 |
| 自动发布拦截 | 规则驱动 | 需要明确质量门禁 |

权限设计原则：

- Agent 默认最小权限
- 写操作必须可审计
- 生产环境操作默认禁止
- 高风险动作必须有人确认
- 所有工具调用保留输入、输出、执行结果和决策依据

## 13. 参考架构

```text
用户目标 / 需求 / PR / 缺陷
        ↓
Orchestrator 编排器
        ↓
┌──────────────────────────────┐
│ Requirement Agent             │
│ Test Design Agent             │
│ API Test Agent                │
│ UI Test Agent                 │
│ Data Agent                    │
│ Execution Agent               │
│ Failure Analysis Agent        │
│ Report Agent                  │
└──────────────────────────────┘
        ↓
工具层：
Git / Docs / DB / API / Pytest / Playwright / Jenkins / Allure / Logs
        ↓
结果层：
测试计划 / 测试用例 / 自动化脚本 / 失败分析 / 质量报告
        ↓
Human Review / Quality Gate
```

架构关键点：

- Orchestrator 负责任务路由、上下文组织和结果汇总
- Agent 负责专业判断，不直接替代质量负责人决策
- 工具层负责真实读取和执行，避免只停留在文本生成
- 结果层必须可追踪、可复核、可沉淀
- Human Review 和 Quality Gate 是质量闭环的一部分，不是可选项

## 14. 分阶段落地路线

### Phase 1：文档与标准先行

目标：

- 明确 Agentic QA 的能力边界
- 定义输出规范、用例规范、风险评估规范和缺陷规范
- 确定哪些场景优先试点

建议优先产出：

- Agentic QA 工作流说明
- AI 输出评估标准
- Human-in-the-loop 规则
- 质量门禁基础规则

### Phase 2：选择一个高价值场景试点

建议优先从以下场景中选择一个：

1. 需求到测试用例自动生成
2. 代码变更驱动精准回归
3. 自动化失败智能分析

优先级建议：

- 如果当前需求评审和用例设计耗时高，先做“需求到测试用例”
- 如果当前发版回归成本高，先做“精准回归”
- 如果当前自动化失败定位耗时高，先做“失败分析”

### Phase 3：接入最小工具链

目标：

- 接入真实输入源
- 接入一个自动化执行入口
- 接入一个报告或日志来源
- 输出可复核结果

可选最小组合：

- Git diff + 测试用例清单 + 回归建议
- OpenAPI + API 用例生成 + Postman/Pytest 执行
- Jenkins + Allure + 失败归因摘要

### Phase 4：沉淀测试知识库与评估闭环

目标：

- 沉淀业务规则
- 沉淀历史缺陷
- 沉淀失败归因规则
- 沉淀 Agent 输出评估结果

关键要求：

- Agent 输出必须能被复盘
- 人工修正结果要反哺知识库
- 评估指标要能持续跟踪

### Phase 5：扩展到质量门禁与平台化

目标：

- 建立发布前质量检查
- 建立自动化执行编排
- 建立质量报告自动生成
- 建立权限、审计和治理机制

阶段边界：

不建议在前期直接建设大平台。应先验证 1 到 2 个高价值场景，再逐步抽象平台能力。

## 15. 与当前仓库结构的关系

当前仓库可以按以下方式承接 Agentic QA 建设：

| 仓库层次 | 承接内容 |
| --- | --- |
| `AGENTS.md` | 定义默认身份、协作原则和加载优先级 |
| `agents/` | 定义不同测试任务下的 Agent 分身 |
| `standards/` | 定义输出、用例、缺陷、风险、评审标准 |
| `skills/` | 沉淀具体能力方法，如接口测试、日志分析、测试数据构建 |
| `templates/` | 沉淀测试计划、测试报告、缺陷报告、风险评估模板 |
| `references/` | 沉淀业务规则、术语、质量基线、历史背景和外部调研指南 |
| `docs/` | 记录架构说明、任务路由、路线图和治理方案 |
| `src/` / `scripts/` / `tests/` | 承接后续工具调用、自检和工程化验证 |

建议后续拆分方向：

- 将“参考架构”和“落地路线”沉淀到 `docs/`
- 将“AI 输出可信度评估”沉淀到 `standards/` 或 `docs/`
- 将“需求到用例”“失败分析”“精准回归”分别沉淀为 `skills/`
- 将测试计划、回归清单、失败分析报告沉淀为 `templates/`

## 16. 主要风险与约束

1. 工具堆砌风险  
   接入很多工具不等于具备 Agentic QA 能力。关键是形成可验证的任务闭环。

2. 无人化误区  
   高风险测试判断、发布建议、生产环境操作不能默认交给 Agent 独立完成。

3. 输出不可验证风险  
   如果 Agent 只给结论、不提供依据，就无法支撑真实质量决策。

4. 编造信息风险  
   Agent 可能编造接口字段、业务规则、日志结论或缺陷原因，必须通过输入约束和人工审核控制。

5. 自动化维护成本风险  
   自动生成脚本如果缺少分层、命名和依赖管理，会快速变成新的技术债。

6. 权限与安全风险  
   查询、写入、环境操作、缺陷提交和发布拦截都需要明确权限边界。

## 17. 下一步建议

建议按以下顺序推进：

1. 将本文作为 Agentic QA 主线蓝图维护，后续具体实现不得直接散落在临时 demo 文件中。
2. 从三个试点方向中选择一个优先落地：
   - 需求到测试用例自动生成
   - 代码变更驱动精准回归
   - 自动化失败智能分析
3. 为选中的试点补充对应 Skill 和 Template。
4. 设计最小输入输出样例，用真实或模拟数据验证 Agent 输出质量。
5. 建立人工审核清单和 AI 输出评估标准。
6. 再决定是否接入工具链和工程化执行能力。

当前最推荐的试点是“代码变更驱动精准回归”。它与企业发版痛点强相关，结果容易验证，也便于后续接入 Git、CI、自动化用例和质量门禁。
